我们先为项目添加了一项小功能，但更复杂的更改需要更完善的流程。GitHub Copilot app 可配合组织现有的工作流程，帮助团队用正确的方法构建所需功能。从本课开始，你将通过几节课遵循典型的智能体驱动开发流程：从议题着手实现功能，确保代码有效、功能符合预期，最终成功将更改合并到项目中。

> [!NOTE]
> 后续功能工作流将沿用同一个会话。通常，不同类型的文件会使用不同会话或拉取请求（PR）；这里会采用简化方式，以便专注于核心概念。

本课中，你将：

- 从 GitHub 议题启动新的智能体会话。
- 在 **Plan** 模式中定义需求。
- 使用 **Autopilot** 模式实现新功能。
- 审查代码。
- 在浏览器画布中手动验证功能。

继续完成此功能时，你将更新存储库指令、自定义现有的 `quality-checks` 技能、添加模型上下文协议（MCP）验证、创建质量保证（QA）智能体并打开功能 PR。

## 场景

Tailspin Toys 的游戏目录不断扩大，访客需要按类别和发行商缩小游戏范围。待办议题描述了功能，但多个类别如何组合等细节需要在编码前达成共识。你将使用 Plan 模式明确这些决策，然后授权 Autopilot 在限定范围内实现功能。

## 背景

将人工智能（AI）编码智能体引入开发流程不会改变基本原则，反而使这些原则更加重要。大多数开发人员遵循类似以下的流程：

1. 打开已有议题，查看待办事项的详细信息。
2. 为需要构建的内容制定计划。
3. 构建并审查代码。
4. 运行测试以验证代码。
5. 手动验证新功能。
6. 创建拉取请求（PR）。
7. 代码通过审查且持续集成流程成功后，合并代码。

> [!NOTE]
> 具体流程会因团队和组织而异，但大多数都是上述流程的变体。

遵循这种标准方法，可以确保 AI 生成的代码满足既定要求，并经过与手写代码相同的审查流程。

## 会话模式

**会话模式**控制智能体的自主程度。可以从提示字段下方的下拉菜单中设置模式，也可以随时更改：

- **Interactive**：你与智能体协同工作。智能体提出更改建议，并等待你的输入后再继续。
- **Plan**：智能体先制定计划。你审查并批准后，智能体才会执行。
- **Autopilot**：智能体完全自主地编写代码、运行测试并迭代，无需等待输入。

先在 Plan 模式中审查计划，再使用 Autopilot 实现。

## 从议题启动会话

开始前，确认星级评分 PR 已合并，并且本地 `main` 已更新。然后从现有议题启动会话，让 Copilot 获得功能需求上下文。

1. 在侧边栏 **Sessions** 下选择 Tailspin Toys 存储库文件夹，然后在存储库顶部导航中选择 **Issues**。打开 **Allow users to filter games by category and publisher**。这是模板预置的议题，无需另建。
2. 选择 **New session**，再选择基于已更新 `main` 的 **new working tree**。

    ![GitHub Copilot app 的议题视图，箭头指向 New session 按钮](../../../_images/app-new-session-from-issue.png)

3. 确认议题已附加到会话，并在模式选择器中选择 **Plan**。

> [!NOTE]
> 如果找不到 Node.js 或 npm，请让智能体运行 `node --version` 和 `npm --version`。如果这两条命令在终端中可运行、但在会话中不可运行，请检查应用的 PATH 或版本管理器设置，然后完全退出并重新打开应用。重试失败的操作和检查；不要仅因智能体找不到 npm 就重新安装 npm。

## 规划筛选功能

先制定计划，才能在 Copilot 编写代码前审查实现方案。由于会话从议题启动，Copilot 已获得功能请求的上下文。发送：

```plaintext
实现此功能。
```

回答 Copilot 的问题，并对照议题的验收标准审查计划。确认计划涵盖类别和发行商筛选、无障碍控件、数据访问改动及测试。讨论尚不明确的行为，例如多个类别如何组合，或没有匹配游戏时应如何处理。

计划应使用项目现有工具运行 lint、单元测试、端到端（E2E）测试和类型检查。将范围限定为实现和测试筛选功能；完成质量工作流后再创建 PR。批准前，要求 Copilot 修改计划，解决其中的问题，并保留议题统一资源定位符（URL）和已达成共识的说明，供后续验证使用。

## 明确批准 Autopilot

对计划满意后，选择 **Approve and implement this plan**，或当前版本中的等效选项。不要假定批准操作会自动切换模式；确认当前模式指示器显示 **Autopilot**。

Copilot 随后会按计划实现功能、生成代码、运行测试并迭代。

> [!NOTE]
> 批准后可能立即开始实现，因此先审查计划。如果 Copilot 报告缺少依赖项或端口冲突，应先解决环境问题，再将检查视为已完成。只停止自己启动的服务器。

## 审查并验证实现

与其他代码一样，生成的代码也需要在合并前审查。先检查实现和测试，再运行站点确认功能表现。

1. 打开 **Changes**，检查筛选功能的实现和测试。
2. 对照议题和已批准的说明检查结果，包括多个类别及发行商组合。确认更改遵循现有存储库指令。
3. 检查 lint、单元测试、E2E 测试和类型检查的结果。跳过的检查不算通过。
4. 接受实现前，解决失败项并重新运行受影响的检查。Playwright 的 E2E 配置会构建并提供预览服务，也可能复用本地服务器；确认被测服务器属于此工作树，而不是上一课留下的服务器。

## 探索新功能

代码看起来没问题，但功能是否正常？让 Copilot 像之前一样启动应用，并在浏览器画布中打开站点。

1. 使用以下提示，让 Copilot 启动应用并在浏览器画布中打开页面：

    ```plaintext
    启动应用，并在浏览器画布中打开。
    ```

2. 稍等片刻，应用将启动，Copilot app 内会打开浏览器窗口。
3. 选择一个类别，确认结果与该类别匹配。清除筛选后，再选择一个发行商并确认结果匹配。
4. 同时应用类别和发行商筛选，并对照议题及已批准的计划检查结果。如果支持多个类别，还要验证已商定的组合行为。
5. 测试没有匹配游戏的组合，并检查空状态。清除或重置筛选，确认完整列表重新显示。
6. 完成后，使用以下提示让 Copilot 停止此会话启动的开发服务器并关闭浏览器画布：

    ```plaintext
    停止开发服务器并关闭浏览器画布。
    ```

## 保留此会话供后续课程使用

现在不要创建或合并筛选功能 PR。保留此会话、工作树和分支，供后续课程继续使用。接下来会将自定义指令应用于筛选代码，再添加技能和 QA 改进，然后创建并合并筛选功能 PR。停止开发服务器后，可以让会话保持闲置；继续后续工作时再返回同一会话。

- 使用 **Autopilot** 模式实现了新功能。
- 审查了代码。
- 在浏览器画布中手动验证了功能。
